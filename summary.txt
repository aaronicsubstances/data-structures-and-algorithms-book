/** CHAPTER 10 **/
// Array list and linked list

Array list: enough for generic list. maintains best performance of O(1) random access of
constant-size arrays. achieves superior time performance of O(1)  
of add/remove operations due to amortisation, which once in a while 
require allocating existing array to another memory location with double or
half the capacity respectively.

Linked list: superior memory management. unsorted version gives O(n) for
random access operations and dictionary operations of insert, find, remove. and so
unsuitable for generic list, but very suitable for specialized data structures or
as a component of other data structures.
singly-linked: enough for stacks and queues
doubly-linked: used for deques and circular lists

/** CHAPTER 11 **/
Linked list, singly-linked, sorted: used for bags/multisets and sets with comparable elements
- simple implementation gives O(n) for insert, find, remove, aka dictionary operations.
- Skip lists implementation gives O(log n) average for insert, find, remove. 
It is intended to be a simpler implementation than hash tables or binary search trees.

Hashtables: used for bags/multisets and sets and does not require elements to be
comparable, unlike skip lists and binary search trees.
also it gives O(1) on average for insert, find, remove, unlike skip lists and binary 
search trees which give O(log n) on average.
collision handling strategies: chaining, open addressing, double hashing.
main disadvantage is that it does not maintain any ordering of elements.

/** CHAPTER 12 **/
Binary search tree, aks BST: it's all about maintaining the invariant that 
the keys of all nodes in the left child are less than the parent key,
and the keys of all nodes in the right child are greater than the parent key.
To support duplicate keys, less than can be changed to less than or greater than.
Operation of remove is the same for all balanced BST variants when
the number of children of the node to be removed is less than 2, because in that
case an adoption occurs.
when removing the key of a node with two non-empty children,
pick math successor of key, ie the minimum key greater than key, from 
leftmost branch of the right, and set it to the key. You can remove that
node before or after setting its key to the place of the node whose key is to 
be removed.

Balancing search trees: it is all about rotations. In a rotation of one child of a
tree to the other side, i.e. either rotating a left child rightwards, or rotating a 
right child leftwards, the old root is demoted and the rotated child becomes the new root,
but the algorithm compensates the old root for the demotion by transfering to it 
a specific child of the new root, i.e. rotating a left child causes it to lose its
right child to the old root, who adopts it as its left child. Similarly rotating a right
child causes it to lose its left child to the old root, who adopts it as its right child.

AVL tree - height-balanced BST: all about fixing balances of BST after updates,
ie add and remove. Requires to store height information in nodes to calculate balances,
because balance calculations assume that height information of children are correct.
    where balance = heights of right child - height of left child
    and abs (balance of node) <= 1
    if balance of node < -1, then we have to rotate left child to the right,
    but before that, check if its right child, ie a grandchild of node, is on the verge
    of imbalance on its right, ie its balance is 1, and if so rotate that
    node's grandchild to the left first,
    before rotating that node's left child to the right.
    if balance of node > 1, then we have to rotate right child to the left,
    but before that, check if its left child, ie a grandchild of node, is on the verge
    of imbalance on its left, ie its balance is -1, and if so rotate that
    node's grandchild to the right first,
    before rotating that node's right child to the left.

Weight-Balance Bounded Tree: very similar to AVL, and so all it's
about fixing balances of BST after updates. Requires to store size information
in nodes to calculate balances,
because balance calculations assume that size information of children are correct.
Storing size information has beneficial side effect of making it possible to find a
key by position or rank.
    where balance of non-root node is = (size of node + 1)/ (size of parent + 1)
    and balance of child node <= BETA
        (at the exact same place in AVL that checks that abs(node balance) > 1)
    and balance of left-right or right-left grand child node <= DELTA
        (at exact same place in AVL that checks if an extra rotation is needed)
    and 0 < ALPHA < 0.5 theoretically, but in practice 2/11 <= ALPHA <= 1 - (sqrt(2)/2)
    and BETA = 1 - ALPHA, GAMMA = ALPHA/BETA, DELTA = 1 - GAMMA

Randomized BST: all about splitting node sometimes during addition.
Requires to store size information in nodes to calculate probabilities
of node splitting during addition, and also for joining node children
during removal of a node with two non-empty children.
This is addition performs split with a probability of 
1/size of node, and joining selects a child node as root of join with probability of
size of child/size of parent. 
Storing size information has beneficial side effect of making it possible to find a
key by position or rank.
The tricky part is with splitting a node: that the left subtree is built by 
inserting into its right child, and never into its left child.
Similarly right subtree is built by inserting into its left child,
and never into its right child.

Splay Tree: all about splaying at the beginning of add, remove and even find as well.
splayMinimum used in remove for a node with two non-empty children,
is a special case of splaying when negative Infinity is passed as keyToUp parameter.
Splay operation is almost same as for AVL/BB rotations, but with different names:
zig - left rotation;
zag - right rotation.
zag-zig - right left rotation;
zig-zag - left right rotation
The new splay operation are zig-zig and zag-zag
zig-zig - left rotation of parent, followed by left rotation of node
zag-zag - right rotation of parent, followed by right rotation of node

Chapter 13

B-tree of order 3 and Red-Black Left Leaning 2-3 tree (invented by Robert Sedgewick)
are equivalent.
The simplicity of the former helps to understand the complex code of the latter.

During the algorithms for addition and deletion of red-black trees, the operation of
flipping colours is equivalent to the operation of merging or splitting nodes in
the algorithms for addition and deletion of b-trees.
also non-existent nodes of red-black trees are considered to be black just like leaves
and the root.

One property I noticed is that in this left Leaning variant of 2-3 red-black tree,
no red node can have exactly 1 child: it must have either zero or 2 children. This
helped me to debug my simulations. Apparently, it is a consequence of the rule that
the paths from the root to a null leaf must be the same for all null leaves.

Another difference between the implementations of left leaning variant and
regular red-black tree is that, the former doesn't need non-null nodes for
null leaves and parents, but the latter does.

The book talks about thinking in terms of coloured links. I only found it helpful,
when I looked at videos by Sedgewick. So I would have loved a clarification
that, the colour of a link is determined by the node
the link is coming down to, and not by the node the link is going up to.
At the beginning of the red-black tree section that was not clear to me. 
The link colouration greatly helped me to understand the reason for the
change of colours which occur during rotation.

Sedgewick's code (https://algs4.cs.princeton.edu/33balanced/RedBlackBST.java.html)
also made me see how to use the tree as a symbol table(aka Map in Java and JS),
and it is simply by storing an additional 'val' field beside the 'key' field.
It also does not use the JS code's approach of using 'side' and 'otherSide' variables
to implement actions with 'left' and 'right' orientations in one routine,
but rather uses two different routines. This use of two routines corresponds
to a similar effort of mine which I employed in the previous chapter, in order to
simulate the JS code which abstract over left and right orientations.
Lastly the code also shows that it is possible to assign -1 to an empty tree, 
instead of zero, so that a 1-node tree has a height of zero instead of one.
This is actually confirmed by Wikipedia (https://en.wikipedia.org/wiki/Tree_(abstract_data_type)).
Thus Sedgewick's code employs the common definition of height of a node,
which counts edges of the node's path to the root, so that a 1-node tree will have
height of zero. And that is in contrast to the other definition
of height of a nnode which counts nodes in the node's path to the root,
so that a 1-node tree will have height of one.

I realized that in the Java code by Sedgewick, the _fixUp routine has an additional
condition for its first if statement, such that it only rotates the left red link
rightwards if the right link isn't red. That additional condition is missing in the
JS code. I presume the omission is justified because if a tree's left and right links 
are all red, even if the JS code initially rotates it to the right, the next if
statement will rotate it back to the left to restore it to the equivalent
in the Java code, which would have skipped the two if statements.

I also realized that in the Java code by Sedgewick, the remove routine has a 
beginning if statement which sets the color of the root to red if its children are
all black prior to entering the _remove routine. That statement is omitted in
the JS code. That statement kind of helped me understand the invariant of
being positioned at a red node or black node with a red left child
prior to the start of any call to the _remove routine.
I presume that the omission is justified because
the _remove routine never examines the colour of the tree parameter itself.
Rather it only examines the colours of the tree's descendants.

Finally, Sedgewick's code ensures that the removal process doesn't start until
the find routine ensures the existence of the key in the tree. The JS code omits
this check, but then has to add extra null checks to avoid errors when 
determining black colours of null leaves, during the removal process of
non-existent keys.

Chapter 14

A heap is a tree data structure that maintains the heap property that a
parent's key is not less than (not greater in the case of min-heaps)
those of its children.
It can be binary (default) or d-ary where d refers to maximum number of
children per node, and it can also be max-heap (default) or min-heap.

It was discovered as a side-effect of the invention of the heapsort algorithm in
the 1960s. In there, the list was the input to sort, and so
heaps based on lists have to obey the extra structure property, which 
is that the tree is a complete tree and the nodes for each tree level appear
in consecutive order in a list.

Later a merger of binary search tree and heap was invented known as treap.
Treap was actually a precursor to randomized BST meant to use statically
assigned random priorities to ensure tree balance on the average.

Note that what the book calls "remove" is extractMin in min heaps and
extractMax in max heaps. And what the books calls top() is min() in min heaps
nad max() in max heaps.

From exercise 14.13, Floyd's heapify algorithm can be used to solve the order 
statistics problem from Chapter 8, if k << n, ie if k is much less than n.


Chapter 15

Chapter is about extension of heaps based on trees and forests introduced in
chapter 12 and 13, which support two extra operations:
1. joining two heaps in running time of O(log n) instead of O(n) if using
Floyd's heapify algorithm. Such heaps are said to be "meldable heaps".
2. support decreaseKey operations for graph algorithms, generalized as changeKey in
the book. Such decreaseKey operations requires a key to have an address,
which is basically the node the key is stored with.
So these extended heaps are said to be "addressable heaps", unlike 
heaps based on static arrays. The node with a key is passed to decreaseKey as
argument. decreaseKey operation is usually the only operation which requires
an extended heap implementation to add "up" or "parent" fields to their nodes. 

Note that what the book calls "remove" is extractMin in min heaps and
extractMax in max heaps. And what the books calls top() is min() in min heaps
nad max() in max heaps.

The extended heap implementations are
- Skew heap - amortized O(log n) for add, extractMin, and decreaseKey operations,
and O(1) for min().
- Binomial heap or Binomial queue - worst case of O(log n) for add, extractMin,
decreaseKey and min.
- Lazy binomial heap - makes worst case of O(1) for add and min, but at cost of 
amortized O(log n) for extractMin rather than worst case O(log n). 
- Fibonacci heap - modifies lazy binomial heap by requiring the use of
circular doubly linked lists in place of left child-right sibling representation of
a node's children, in order to support deleting a node without having to search
first for its previous node, as would need to be done in a singly linked list,
in implementing decreaseKey.
Goal is to reduce running time of decreaseKey from worst case of O(log n) to
amortised O(1). And it does this, by separating the node, and adding it to
the forest of heap-ordered binomial trees (resembles a decreaseKey implementation for
skew heaps).
Except that mark the parent as having lost a child,
and next time it has to lose another child, recursively separate the parent too.
The analysis of decreaseKey's running time depends on Fibonacci sequence, hence the
name of the data structure is Fibonacci heap.
- Pairing heap - simplification of Fibonacci heap which does not care about the order
or degree of the subtrees.
It is a multiway heap-ordered tree based on left-child right-sibling representation
rather than circular list.
The merge function is like that of merging 2 binomial trees of the same order, where
one becomes the new child of the other.
The decreaseKey function is like that in Fibonacci heap, but skips the need to
separate if the new key isn't smaller than that of the parent's key.
The extractMin function (called "remove" in the book) calls the merge function
indirectly, by merging two trees at a time recursively through a mergeByPairs
helper function, hence the name of the data structure is pairng heap.

Chapter 16

Digital search tree implementations
- prefix tree or trie
- radix tree or compact trie - no node aside the root can have exactly 1 child.
- ternary search tree or ternary trie - interesting look-alike of binary search
tree, whose nodes have the usual left and right pointers. They have an
additional middle pointer for navigating the strings stored in the structure
one character per middle pointer.

Chapter 17

Variants:
- directed graph vrs undirected graphs
- weighted graph vrs unweighted graphs
- multigraph vrs simple graph
- cyclic or acyclic.

NB: Trees are directed acyclic graphs.

Graphs in this book are all simple graphs, ie no self-loops and at most 1 edge
in the same direction between a given pair of vertices.
Weights of weighted graphs in this book are never negative.

Types of representations:

 - adjacency matrix for dense graphs
 - adjacency list for sparse graphs
 - adjacency set - basically adjacency list but with linked list or array-based list
swapped out for some advanced data structure like hash set or tree.

Book uses convention of using adjacency matrices throughout its algorithms,
for making the algorithms easier to understand, and is fully aware that
most algorithms are more suitable (and sometimes faster) with the adjacency
list representation.
Another convention in the book is the use of 0 value in an adjacency matrix
at address i,j to indicate that the ith vertex and the jth vertex are not connected. 

Shortest Path Algorithms:

 - Floyd-Warshall algorithm - shortest paths between all possible vertices. more suitable with
adjacency matrix. O(v^3)
 - Bellman-Ford algorithm - shortest paths between a vertex and all other vertices. more suitable
with adjacency list. O(v * e)
 - Dijkstra's algorithm - shortest paths between a vertex and all other vertices, or
shortest path between two vertices. more suitable with adjacency list. requires
an efficient addressable heap implementation. O(v * log v)

Topological Sort Algorithms:
- Kan's Algorithm - focuses on absence of incoming edges. discovers sort in order.
more suitable with adjacency list. 
- Tarjan's algorithm - focuses on absence of outgoing edges. discovers sort in reverse order.
more suitable with adjacency list. 
useful also for detecting cycles in graphs.

Detecting connectivity in graphs:
- algorithm based on a disjoint-set data structure, which is a forest of
trees used as a JS Set which supports only has() and union() operations.
Only difference with forest of trees implementation in previous chapters
on trees is that instead of a parent node storing the pointer
to its child, here a child node stores the pointer to its parent.
this data structure is also used in Kruskal's algorithm
NB: this algorithm can also determine count of connected subgraphs of a grah.
- kind of depth-first search tree algorithm. more suitable with adjacency list.

Minimum Spannning Trees (MST) Algorithms:

Their input graph parameter must be a weighted undirected graph.
In the book, the graph parameter also has to be connected for the 
MST implementations to work. 

- Prim's Algorithms - more suitable with adjacency matrix. Focuses on vertices.
Makes use of an addressable heap.
Does not seem to work for disconnected graphs at all unless 
connected subgraphs are first found and then the algorithm is run on each subgraph.

- Kruskal's Algorithm - more suitable with adjacency list. Focuses on edges. uses
a disjoint-set data structure used elsewhere for detecting graph connectivity
as noted above.
Seems to be capable of being adapted to work directly on a disconnected graph
by retrieving the multiple spanning trees from the disjoint-set data structure.

Chapter 18

Arrays and data structures based on them array-based lists, hash tables and
array-based heaps are just not amenable to functional programming, ie can
have an equivalent that respects functional programming constraints and 
preserves to a good extent the performance of the original.

Linked list is amenable, and so is stack. Queues are amenable with the use of
a data structure based on two stacks, as was done in exercise 10.12

The way to amenability for linked lists is to duplicate new nodes for the path 
from the head to an inserted or removed node position, and reuse the tail.

Doubly-linked list, deques and circular lists are not amenable, because in the
end every node will have to be duplicated.

Binary trees and digital search trees can be made amenable.

Meldable heaps can be made amenable if not dependent on data structures that are
not amenable, like how Fibonacci heaps depend on circular lists which is not amenable.

The way to amenability for trees is to duplicate new nodes for the path 
from an inserted or removed node to the root, and reuse the unmodified subtrees.
